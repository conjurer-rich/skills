# Pick

1. Run `delegate-status status --cache <scratch>/pick-cache.json --sync-labels`. Its `issues` are every open `<label>` issue in the skill's order: issues with the first rank label, then the second, then unranked; oldest `createdAt` first within each group. Each carries a `state`, `counts` tallies them by state, and `pick` names the issue step 2 takes (`{number, title}`, or `null`):
   - `delegated`: an open PR from a `<branch_prefix><n>-` branch exists (`pr`). Skip an issue that has an open PR from a `<branch_prefix><n>-` branch: it is already delegated.
   - `claimed`: another session holds a live claim on it (`holder`): skip an issue another session holds a live claim on.
   - `blocked`: an issue or PR it depends on is still open (`blocked_by` lists only the open ones). Skip it; it frees itself on the pass after its last blocker closes or merges.
   - `waiting-on-human`: a delegator question or derived criteria wait on the human, as **Work** step 3 defines it (`reason`). Skip it. It carries `<answer_label>` (**Derived labels** below) until the human replies or 👍s. An unanswered question (`question-unanswered`) wins over any criteria: an issue with criteria in its body, or confirmed derived criteria, still waits while a later question has no human reply. The human answers by replying; an edit to the issue body is no answer.
   - `held`: this session holds the claim; it carries `criteria`, a waiting `reason` or `blocked_by` like any other.
   - `free`, with `criteria` `body`, `confirmed` or `none`.

   **Order.** The first that applies wins: `delegated`, then a live claim (`claimed` or `held`), then `blocked`, then an unanswered question, then the criteria. A live claim on a blocked issue still reads as `claimed`; a blocked issue is not also asking the human for anything, so it carries `<blocked_label>` and not `<answer_label>`.

   **Dependencies.** An issue's blockers are the union of GitHub's native "blocked by" dependencies (`GET /repos/<owner>/<repo>/issues/<n>/dependencies/blocked_by`; where that route answers 404 it is not asked again that pass), the `#N` references under a `## Dependencies` heading (up to the next heading), and the `#N` references on any line containing `Blocked by` (any case, several per line). A native dependency links issues only, so a PR blocker is written in the body. A closed issue or merged PR blocks nothing; neither does a mention of `#N` anywhere else.

   **Derived labels.** `<answer_label>` and `<blocked_label>` are derived, not state. `--sync-labels` recomputes them on every Pick and Watch pass from the classification it has just made: `<answer_label>` on each `waiting-on-human` issue (or `held` one with a waiting `reason`), `<blocked_label>` on each blocked one, `<review_label>` on each delegated PR awaiting the human (**Watch** step 3), and none on any other item. It creates a label the repository lacks, leaves an issue another session has claimed alone, and names the issues it changed under `labels_synced`. Pass `--answer-label`, `--blocked-label` and `--review-label` when the project renamed them. State comes from the comments and dependencies alone, so a human who adds or removes either label by hand changes nothing, and the next pass puts it back. The delegator never sets them any other way.

   An issue marked `stale_label` carries `<progress_label>` but has no live claim, so it is free: remove the label as **Stale label** in **Claims** says, and keep it as a candidate.

   **Skip cache.** `--cache` keeps `pick-cache.json` in the run's scratch directory with, per skipped issue (`claimed`, `blocked` or `waiting-on-human`), its `updatedAt` and `checkedAt`, and for a `blocked` one each blocker's `updatedAt`. The script re-reads a cached issue's comments **only** when its `updatedAt` is later than the cached value, it was `claimed` and `claim_ttl` has passed since `checkedAt`, or it was `blocked` and any blocker's `updatedAt` has moved (a blocker closing does not move the blocked issue's own `updatedAt`); a skip it reuses carries `cached: true`. A human reply to a question moves `updatedAt`, so the next pass re-reads the issue and frees it. A 👍 on derived criteria does not, so `criteria-unconfirmed` is never cached. The aborted run re-read every skipped issue's body and comments on every loop pass when nothing on them had changed.
2. Take the first issue that is not waiting on the human and that no other session has taken, as `pick` names it: the first `free` one, or a `held` one with `criteria` (not a waiting `reason`). Read `pick` as it is printed; never re-derive it with your own `jq` filter over the status, because a filter on a key the output does not have yields nothing and reads as "no issue to pick". Continue at **Work** with it. If Work then loses the claim race for it, come back here and continue with the next `free` issue after it in `issues`.
3. If `pick` is `null`, say so, quoting `counts` (the number of issues in each state) and naming the claimed ones, and stop. A report of nothing to pick whose `counts` has a `free` entry is wrong: re-read `pick` before sending it. Do not widen the search. A cached skip is reported once per run with its reason, on the pass that first skips it, not re-explained on every pass.
