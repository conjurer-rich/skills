# Work `#N`

1. **Eligibility.** `delegate-status issue N`. If it prints `not-eligible`, the issue is closed or lacks the label: reply in chat "Issue #N is not labelled `<label>`; add the label to make it eligible" and stop. Keep its output for step 3, and read the title and body with `gh api repos/<owner>/<repo>/issues/N --jq '{title, body}'`.
2. **Budget.** Run `delegate-status budget` (Pick's status already holds it). Reclaim finished worktrees first, then count.

   **Reclaim.** Reclaim each `worktrees.reclaim` entry as `references/reclaim.md` says, and name each `worktrees.keep` entry in the report.

   **Count.** `budget` holds the delegated worktrees left after reclaim and the open PRs from all authors. If `at_limit` is true, either count is at its limit: post this issue comment (`delegate-status comment N --body-file <file>`) and stop:

   > Delegation paused: <k> delegated worktrees active (limit <max_worktrees>) and <m> open PRs (limit <max_open_prs>). Retry when one closes.

   **Claim.** `delegate-status claim N` (**Claims**). If it exits 4 (`lost`), another session holds the issue: stop. If it prints `won` with an `open_pr`, a session opened a PR from a `<branch_prefix>N-` branch and released its claim since Pick looked: once claimed an open PR from a `<branch_prefix>N-` branch now exists, so release with `--delete` and stop. When Pick started this Work, return to Pick's next candidate instead of stopping. Every stop from here on releases the claim. Once the claim is yours, set the **Session title** to `#N <issue title>`. Then start its heartbeat and write `item_start_calls` to `run-state.json`.

3. **Acceptance criteria.** Step 1's output says which case holds, the first that applies in this order (a `held` issue carries the same `criteria` or `reason`):
   - `waiting-on-human` with `question-unanswered`: a delegator question (it starts with `**Question before delegation**`) has no later comment from the human: one that contains neither `<!-- delegator` nor the Claude Code footer and whose author is not a bot. An open question wins over any criteria, in the body or confirmed, because the delegator is waiting on its answer. Only a reply answers it: an edit to the issue body does not, since REST gives no time for the last body edit.
   - `criteria: body`: the body has a heading matching `/acceptance criteria/i` followed by a numbered or bulleted list. Use them for the rest of the run.
   - `criteria: confirmed`: a derived-criteria comment (it starts with `**Acceptance criteria (derived by the delegator`) carries the 👍 of the authenticated login. Only that login's reaction counts, because anyone can react on a public repository; the delegator never reacts, so that login's 👍 is the human's. Read the comment (the last one starting with that heading in `gh api --paginate repos/<owner>/<repo>/issues/N/comments`) and use its current text, including any edits, for the rest of the run.
   - `waiting-on-human` with `criteria-unconfirmed`: a derived-criteria comment without that 👍.
   - `criteria: none`: there are none yet.

   On either `waiting-on-human` reason, say in chat that issue #N is waiting on the human, post nothing, and stop.

   On `criteria: none`, derive the criteria and stop. First load `find-gaps` on the issue body and every human comment, including answers to earlier questions. If the intent has two plausible readings, or the gaps leave no observable outcome, post one question as a comment that starts with `**Question before delegation**`, names the readings or gaps, and ends with the delegator marker, then stop. Otherwise derive 2–6 criteria, each observable and testable, and post them as a comment ending with the delegator marker:

   > **Acceptance criteria (derived by the delegator; edit this comment to change them, then react 👍 to confirm)**
   > 1. …

   Say in chat that issue #N awaits criteria confirmation, and stop. The run that follows the 👍 starts again at step 1.
4. **Size check.** If the criteria cannot be met by one PR of the project's usual size (`delegate-status merged-sizes` reads two recent merged PRs for the norm), load `story-splitting`, post the split as an issue comment, work the first child, and file each remaining child as its own issue with the `follow-up` label and no `<label>`. Say so in the PR body under **Found on the way**.

   **Tier.** Read `references/tiers.md`. Name the tier you expect from the criteria and the size check; the brief and the implementer's model in step 6 depend on it. Expect **S** only when the issue's title, body, acceptance criteria and any paths it names clearly scope the work to one package (`tier_small_max_packages`), within `tier_small_max_lines`, and name nothing matching a `risk_paths` glob; any doubt predicts **not S**. Record the expected tier and a one-line reason in `run-state.json` (`expected_tier`, `expectation_reason`) and in the run's report. Step 7 measures the real tier from the staged diff and records it in the PR body's **Summary**.
5. **Worktree.** From the main checkout, `git fetch origin <default branch>`, then `git worktree add <path> -b <branch_prefix>N-<slug> origin/<default branch>`, where `<path>` is a directory outside the main checkout, such as `../<repo>-worktrees/N-<slug>`. Stay in the main checkout: the delegator never enters the worktree (**Hand-back contract**). Create the marker directory `<path>/.delegator/` with a file `run` holding the session name, so the stop hook stays quiet while staged work waits there, and make sure `.delegator/` is listed in the main checkout's `.git/info/exclude` so it is never staged. Then dispatch a bootstrap subagent on `model: <mechanical_model>`, briefed with the path and the exact bootstrap commands from the project's root CLAUDE.md (for a pnpm monorepo: `pnpm install` then `pnpm build`), under the Hand-back contract; it returns `pass`, or `blocked` with the failing command's last line, in which case go to **Blocked**. Keep the worktree until its PR merges; the **Reclaim** sub-step of the next run's budget check removes it then. Never remove a worktree whose PR has not merged.
6. **Handoff.** Renew the claim (**Claims**), then dispatch one subagent with `subagent_type: general-purpose`, `model: <implementer_model_small>` when step 4 expected S and `model: <implementer_model_large>` otherwise, `run_in_background: false`. The brief is self-contained (**Hand-back contract**) and contains, verbatim from the sources: the issue title and body, the acceptance criteria, the worktree absolute path, the project's root and `.claude/` CLAUDE.md pointers to skills, the project's **Verification scope** section when it has one, any hand-off comment's **Traps** line, and these instructions:

   > Work only inside `<worktree path>`. Load the `tdd` and `testing` skills before any code change; RED before GREEN for every behaviour change. Run the project's pre-push self-check and every quality-gate step of `<pre_pr_gate>` yourself, including any glossary or vocabulary check; stop short of its PR-creation steps. Do **not** open the PR and do **not** commit; leave the changes staged. Use `VITEST_MAX_WORKERS=2` for every test run. While working, run only the affected package's or file's tests. For verification, run lint, typecheck, build and the tests of the packages the diff touches, plus the mutation gate on the diff. Do not run the complete test suite: CI runs it on the PR. Where the self-check or gate asks for the complete suite, record that CI runs it. If the previous test run in this worktree was killed, run `pnpm test:db:clean` before the next one. Write to `<scratch>/<N>/implementer.md`: (a) the list of files changed, (b) for each acceptance criterion the test name that proves it, (c) the RED-before-GREEN evidence per the gate, (d) the mutation gate outcome or `N/A` with alternate evidence, (e) the exact commands you ran for verification and their last ten lines, (f) anything you noticed but did not fix, (g) the output of `git diff --cached --shortstat` and the packages the staged diff touches, (h) `rendered change: yes` when any changed file can alter what a user sees rendered, else `rendered change: no` (tests, types, and code no rendered output depends on). Return at most ten lines: that path, `pass` or `blocked`, the shortstat line, the package count, the (h) line, and one line per acceptance criterion reading `Covered` or `not`.

   The brief adds, when each applies (`references/tiers.md`):
   - The project has a **Verification scope** section: `For verification, follow the Verification scope below in place of the default scope above and of the gate's complete-suite step.`
   - Expected tier S: `Write no plan document and run no planning or progress-tracking agent; keep the change to the criteria.`
   - `preflight` is set: `After your last code change and before your final verification, run these commands in order from the worktree root: <preflight>. Stage what they change with git add -u and list any new untracked file in (f). A failing command is a blocked return.`
   - `local_full_suite` is on, or a changed file matches a `full_suite_paths` glob: the paragraph below.

   When the complete suite runs locally, the brief adds:

   > Then run the complete test suite once, at the end, as a background task, and wait for it to exit (Monitor or a polling loop, never a fixed sleep), then read its exit code and summary; do not return before it exits. Never run it in the foreground or pipe it through `tail`.

   The implementer's (a) is the delegator's only list of changed files; the delegator reads it from the file and never runs `git diff`. If the subagent returns `blocked`, go to **Blocked**, unless **Escalation** applies.

   **Escalation.** When an implementer on `<implementer_model_small>` returns `blocked`, here or in step 9, or its diff measures not S (step 7's measurement from its (g), or the tier S reviewer's `tier: not S`), renew the claim and dispatch one fresh implementer on `<implementer_model_large>` with the same brief, plus the earlier attempt's outcome: its verdict, its report path and the reason for escalating. The worktree and its staged changes stay; the brief says they are the earlier attempt's, to keep, fix or rework. It replaces the earlier implementer for the rest of the run, and its return restarts step 7 (in step 9 it also counts as the repair round, with the blocking findings in its brief). Escalate at most once per run, never from `<implementer_model_large>` to `<implementer_model_small>`, and record it in `run-state.json` (`escalated`) and the report. A `blocked` after escalation goes to **Blocked**.
7. **Independent checks.** The implementer's returns are claims, not evidence. Renew the claim. Measure the tier (`references/tiers.md`) from the implementer's (g) and its list of changed files; not S from an implementer on `<implementer_model_small>` goes to **Escalation** (step 6) first. Then dispatch the checks for that tier on the staged diff, each at its default model. None of them edits files. Each is briefed with the worktree path and the Hand-back contract: its full report goes to `<scratch>/<N>/checks/<process|acceptance|whole-diff>.md`, and it returns at most ten lines, the path, `pass` or `findings`, and the count of blocking findings. The delegator reads a file's verdict table or findings list only in step 9. No tier skips independent verification. The RED-before-GREEN evidence goes in the PR body at every tier.
   - **Tier S.** Dispatch one independent reviewer, the project's single self-review: the **Whole diff** check below, with its brief extended. It also checks each acceptance criterion against the tests, as **Acceptance** does, and reports a verdict per criterion in `acceptance-review`'s words. The implementer's criterion-to-test mapping and its RED-before-GREEN evidence go in as claims to check. The tier is a claim too: the reviewer re-measures it with `git diff --cached --shortstat` and the changed files' packages, and returns `tier: not S` when the diff is over a threshold or touches a `risk_paths` glob. Only when it returns `tier: not S`, dispatch **Process** and **Acceptance** as at tier M before step 8; this does not use up the repair round. The report goes to `<scratch>/<N>/checks/whole-diff.md`.
   - **Tier M or L.** Dispatch these three read-only checks in parallel:
     - **Process.** The project's `tdd-guardian` agent, or else a subagent that loads the `tdd-guardian` skill.
     - **Acceptance.** A `general-purpose` subagent that loads `acceptance-review`. It takes the step 3 criteria as the contract and the staged diff with its tests as the evidence, and returns a verdict for each criterion. The implementer's criterion-to-test mapping goes in as a claim to check, not as the evidence.
     - **Whole diff.** The project's whole-PR review agent (`pr-reviewer` when the project defines it). Otherwise, a `general-purpose` subagent that runs `<correctness_review>` on the staged diff and returns its findings without applying them.
8. **Walkthrough.** If `walkthrough` is on, a changed file matches `walkthrough_paths` in the implementer's (a), and its (h) reads `rendered change: yes`, renew the claim and dispatch one walkthrough subagent (`general-purpose`, default model, `run_in_background: false`). A test-only diff matches none of the defaults, so it never boots the stack. The brief carries the worktree path, the changed UI files, the Hand-back contract and these instructions: load `browser-ux-walkthrough` and the project's stack skill; boot the stack per the Recipe, sign in, grade the changed surfaces in the Checklist sections and themes its **Scope** step selects (where the stack skill has a *Themes* rule, that rule picks the themes; both themes only without one), and save every screenshot under `<scratch>/<N>/<surface>-<theme>-<before|after>.png`; do **not** run its Fix step: you do not write production code; with no findings, stop the stack; with findings, leave it running for step 9's re-walk; write the grades table, the sections skipped with the reason and every `finding` to `<scratch>/<N>/walkthrough.md`; return at most ten lines: that path, `pass` or `findings`, and the count of `finding` rows. The delegator never runs `agent-browser`: in the aborted run its snapshots were the largest item in the transcript. When a changed file matches `walkthrough_paths` but (h) reads `rendered change: no`, skip the walkthrough and write `Walkthrough: n/a — no rendered change` as the section body. If the subagent returns that the stack could not boot, file a `follow-up` issue titled `Walkthrough blocked for #N: <reason>` and use `Walkthrough blocked: <reason> (see #<follow-up>)` as the section body.
9. **Repair round.** Collect every blocking finding from steps 7 and 8:
   - any `tdd-guardian` finding;
   - any criterion that `acceptance-review`, or the tier S reviewer, does not rate `Covered` (`Partial`, `Missing`, `Regressed` and `Unverified` all block);
   - any `pr-reviewer` finding rated Critical or High Priority, or any `<correctness_review>` correctness finding;
   - any walkthrough `finding`.

   A finding that names only code the diff does not touch is not this PR's: apply **Not this PR's** in `references/review.md` instead of blocking on it. Lesser review findings (`pr-reviewer` Suggestions, `<correctness_review>` cleanups) go to the PR body's **Found on the way** section. If nothing blocks, skip to the last paragraph of this step.

   Otherwise renew the claim, then send the implementer subagent one message (`SendMessage`, not a fresh dispatch) carrying every blocking finding, copied from the check files' findings lists and the walkthrough file, and wait. It fixes them, re-runs the same checks as step 6, limited to the files its fix touched (the complete suite only when `local_full_suite` is on), and returns (a)–(g) afresh under the Hand-back contract: the fresh report overwrites `<scratch>/<N>/implementer.md`, and the return is again the path, the verdict and one line per criterion; the PR body uses those returns, not the first ones. It may propose deferring a walkthrough or whole-diff finding with a one-line reason. You decide: accept a deferral only when the finding lies outside the acceptance criteria, and file each accepted one as a `follow-up` issue. Unmet criteria and `tdd-guardian` findings cannot be deferred.

   Then re-run the checks for the tier, measured again from the fresh (g): at tier M or L, `tdd-guardian` and every check that reported a blocking finding, as step 7 dispatches them; at tier S, the one reviewer. If the walkthrough had findings, send the walkthrough subagent one message naming the affected surfaces; it re-walks them on the stack it left running, in the themes it graded, for the `-after.png` shots (restarting a server per the Recipe only when that server does not reload changed files), stops the stack, and returns the path and the count of findings left. The re-walk never runs in the main session. Whenever a run leaves this step without that re-walk while the stack is up (the implementer returned `blocked`, or the **Stop rule** tripped), first send the walkthrough subagent one message to stop the stack.

   One round only. Any blocking finding that remains goes to **Blocked**, with the findings in the **Verification** section.

   On every path out of this step except **Blocked**, write the `## UX walkthrough` section from the final grades, `Walkthrough: n/a — no rendered change`, or `Not applicable: no changed file matches walkthrough_paths` when the walkthrough did not run.
10. **Commit.** Write the commit message to `<scratch>/<N>/commit-message.md`: a conventional-commit subject that names the issue (`fix(web): … (#N)`) and the project's co-author trailer. Write the PR body to `<scratch>/<N>/pr-body.md` per the **PR body contract**:

    - `Summary` links the issue (`Closes #N`) and names the tier with its measurement (`Tier S: +83/−4, 1 package, no risk path`).
      Then one view of the change, the smallest that makes it clear: pseudocode, a call tree, a component or file tree, a Mermaid diagram, or a diff sketch of one of those. Keep only the calls, files and states the reader needs; leave the view out when one sentence says it all.
      Then a merge-danger line: `Door: two-way` when a revert undoes the change, `Door: one-way` when it cannot (a destructive migration, deleted data, a published contract), and `Blast radius:` naming who or what a bad merge would hit (`Blast radius: the invoice page only`).
    - `Acceptance criteria` lists each criterion with the test name that proves it.
    - `TDD evidence` and `Mutation gate` carry what the implementer returned.
    - `Verification` opens with the scope line from `references/tiers.md` (`Verification scope: project` or `default`), then the exact commands and their last lines.
    - `UX walkthrough` carries the walkthrough skill's output, `Walkthrough blocked: …`, `Walkthrough: n/a — no rendered change`, or `Not applicable: no changed file matches walkthrough_paths`.
    - `Found on the way` lists observations, any `follow-up` issues filed and any finding that was not this PR's.
    - `Preview E2E` carries the oracle state or `Oracle off: informational until #<oracle issue> merges`.
    - End with the project's PR footer; step 14 appends the cost line.

    When **Run** started this Work, commit without asking: the PR is the checkpoint, and nothing merges before the human reviews it. Otherwise ask the human for commit approval with the proposed message shown, **before** you ship. Then ship inline, as the **Hand-back contract** says: renew the claim, then `git -C <worktree> commit -q -F <scratch>/<N>/commit-message.md`, output to `<scratch>/<N>/ship.log`. The delegator commits only from the message file and runs nothing else in the worktree.
11. **Evidence.** If there are screenshots under `<scratch>/<N>/`, dispatch one evidence subagent on `model: <mechanical_model>` after step 12 creates the PR, briefed with the worktree path, the screenshot paths, the PR number and the project's evidence rule as exact commands (for Flow Canvas: the `ux-evidence` orphan branch, path `<pr-number>/<surface>-<theme>-<before|after>.png`), and the Hand-back contract. It pushes them, edits the body's walkthrough links with `delegate-status pr-edit <PR> --body-file <file>`, and returns the evidence commit SHA. Without screenshots there is no dispatch.
12. **PR.** Renew the claim (**Claims**) before pushing, then `git -C <worktree> push -q -u origin <branch>` (never with a force flag) and `git -C <worktree> rev-parse HEAD` for the head SHA. Then `delegate-status pr-create --head <branch> --title "<subject>" --body-file <file>`; add `--draft` when `land` is on, so that the human's Ready-for-review click is the landing signal. Then `delegate-status comment N --body-file <file>` on the issue: `Opened <PR URL> for this issue.`, ending with the delegator marker. A failing command goes to **Blocked** with the log's last lines. Then the delegator releases the claim and stops its heartbeat; the release takes `<progress_label>` off the issue: from now on the open PR marks the issue as taken. Subscribe the PR as **Watch** step 6 says, set `worked_issue` in `run-state.json`, and set the **Session title** to `PR #P (#N) <issue title>`.
13. **Oracle.** If `oracle` is on, wait up to 20 minutes polling every 2 minutes for the sticky comment and apply the Preview oracle rule. Otherwise say the check will run on the next `Review`. Any wait for CI uses `delegate-status checks <PR> --head <sha>`, pinned to the head just pushed; no checks yet is pending, never green.
14. Write the cost note (`references/handoff.md`) last, after steps 11 and 13 have finished editing the body. Report the PR URL and stop. This session has now worked its one issue: the **Stop rule**'s hand-off threshold is reached.
