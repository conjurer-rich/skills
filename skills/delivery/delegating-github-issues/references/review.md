# Review `#PR`

1. Confirm the PR head branch starts with `<branch_prefix>`; otherwise say this PR was not opened by a delegated run and stop. Then claim the PR (**Claims**); if another session holds it, stop. Once the claim is yours, set the **Session title** to `Review PR #P <PR title>`. Then start its heartbeat.
2. Find its worktree: `git worktree list --porcelain | grep -B2 'branch refs/heads/<head branch>'`. If none exists (another machine or session opened the PR), `git fetch origin <head branch>`, then `git worktree add <path> <head branch>`, then dispatch the bootstrap subagent as **Work** step 5 does. Never enter it: every later command against it runs in a subagent briefed with its path.
3. Run `delegate-status pr <PR>`. When it carries a `handoff`, read that comment first: its **Next** step is where to start, its **Verified** lines need no re-deriving, and its **Traps** go into the implementer brief. Its `items` are what needs an answer (see **Delegator marker**): each unresolved review thread whose last comment needs one (`kind: thread`, with the `thread` id, which is the thread's first comment and the one a reply answers, `path` and `line`), and each top-level comment (`comment`) and review body (`review`) that needs one, with its `id`, `login` and `body`. The script reads the PR's top-level comments and its reviews' bodies as well as its threads.
4. For each thread, classify the last human comment: **actionable** (names a change, a file, or a behaviour) or **ambiguous** (a question with two readings, or a preference without a target). Post one reply on each ambiguous thread with exactly one question and stop after handling the actionable ones. Every reply ends with the delegator marker. Reply in a thread with `delegate-status reply <PR> <thread> --body-file <file>`. For a top-level comment or review body, reply with `delegate-status comment <PR> --body-file <file>`, whose body starts by quoting the comment's first line (`> …`) and ends with `<!-- delegator reply-to: <comment id> -->` in place of the plain marker.

   A comment that asks for findings as follow-ups needs no code. File each finding as its own issue with the `follow-up` label and no `<label>`, with acceptance criteria. Add each issue to the PR body's `## Found on the way, not fixed here` section (`delegate-status pr-edit <PR> --body-file <file>`), then reply naming the issues. The body is where **Land** learns which findings are accepted.
5. Renew the claim, then hand the actionable threads to the implementer subagent (same brief shape as **Work** step 6, with the thread bodies and paths in place of the issue; its model follows a tier expected from the threads as **Work** step 4 says, with **Escalation**), then run **Work** steps 7–9, with the tier measured from this staged diff. For the acceptance check, the contract is the actionable thread requests plus the PR body's acceptance criteria, which the fix must not break. Run the walkthrough only if `walkthrough` is on and a changed file matches `walkthrough_paths`.
   When **Watch** or **Land** started this Review and the implementer cannot pass the gate, or a blocking finding survives the repair round, have the implementer subagent discard the staged changes (`git restore --staged --worktree .`), reply on each actionable thread or comment with the failure in one sentence, and stop; under Land, go to **Bail-out**. Never go to **Blocked** from **Watch** or **Land**. When the human started this Review, the PR already exists, so **Blocked** does not apply: keep the staged changes, post the remaining findings as one PR comment ending with the delegator marker, and stop.
6. Commit after approval; when **Watch** or **Land** started this Review, commit without asking. Renew the claim, then ship inline as **Work** steps 10 and 12 do, without PR creation: it commits from the message file and pushes with no force flag, and `rev-parse` gives the head SHA. Then reply on each actionable thread or top-level comment with one sentence naming the commit and what changed, ending with the delegator marker (the `reply-to` form for a top-level comment). Do not resolve threads; the reviewer resolves. Then run `delegate-status review-status <PR> --addressed <n>`, with `<n>` the threads and comments this round answered: it rewrites one line at the top of the PR body, `**Ready for re-review (round <k>):** addressed <n> comments in <head>`, with a link to the changes since the human's last review. GitHub never notifies the human of work done through their own login, so this line and `<review_label>` are how they learn the PR is theirs again.
7. Apply the Preview oracle rule if `oracle` is on. Report and stop.

## Not this PR's

A review finding, or a red check, that names only code the diff does not touch is not this PR's when the same thing fails on the default branch: the same finding exists in that code on `origin/<default branch>`, or `delegate-status checks --ref <default branch>` shows the same check red. Then:

1. Look for its key in the PR's `not_this_pr` (from `delegate-status pr`): `check:<check name>` or `finding:<file>:<rule or one-word topic>`. When it is there, the PR already said so: go to step 4.
2. File a `follow-up` issue with `delegate-status issue-create --title "<check or finding> fails on <default branch>" --body-file <file>`, which reuses an open one with the same title.
3. Comment once on the PR with `delegate-status comment <PR> --body-file <file>`: what fails, that it fails on the default branch too, the follow-up issue, the line `<!-- delegator not-this-pr: <key> -->`, and the delegator marker. List it under the body's **Found on the way**.
4. Carry on as if it had passed: it does not block the repair round, **Blocked**, Land's CI gate or the merge, and the PR is never widened to fix it. Code the diff touches is never covered by this rule.

When the same failure does not reproduce on the default branch, it is this PR's after all, whatever file it names: treat it as any other finding.
